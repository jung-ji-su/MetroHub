MetroHub는 서울시 공공 API에서 수집한 실시간 지하철 데이터를 Kafka 스트림으로 처리하고, SSE를 통해 클라이언트에 Push하는 이벤트 기반 실시간 플랫폼입니다. 단순 CRUD 서버를 넘어, 데이터 수집 → 스트림 처리 → 실시간 전달 → 프론트엔드 렌더링까지 전체 파이프라인을 직접 설계하고 구현했습니다.

01
대용량 실시간 데이터 처리

24개 노선 × 수백 개 역을 CompletableFuture 50-스레드 병렬 조회로 처리하고, ConcurrentHashMap으로 중복 열차 데이터를 ETA 최솟값 기준 실시간 제거. Kafka 파티션 키(lineNumber)로 같은 호선 이벤트의 순서를 보장합니다.

02
분산 인프라 설계 · 운영

SSE Long-lived 커넥션 고갈 문제를 subway-notification 서비스 분리(MSA)로 해결. Kubernetes HPA · nginx Ingress · PVC 포함 전체 인프라를 직접 구성하고, Kafka 재시작 오류 · PVC 권한 문제 등 실제 장애 6종을 트러블슈팅했습니다.

03
CI/CD 자동화 — 이원화 파이프라인

4개 서비스 테스트→빌드→배포를 GitHub Actions(클라우드)와 Jenkins + k8s(로컬)로 이원화 자동화. 이미지를 BUILD_NUMBER 태그로 누적 보관해 rollout undo 즉시 롤백 전략을 수립했습니다.

04
0-1 BFS 알고리즘 — 최소 환승 경로 탐색

같은 노선 이동(비용 0)과 환승(비용 1)이 혼재하는 문제를 Deque 기반 0-1 BFS로 O(V+E) 시간 내 해결. Dijkstra보다 단순하고 이 문제 구조에 최적인 알고리즘을 선택해 24개 노선의 최소환승 경로를 실시간 계산합니다.

5분 자동 해제

서울 지하철 데이터는 30초마다 Kafka에 수신됩니다. 임계값 초과 시마다 경보를 발행하면 10분 혼잡 지속 시 20번의 중복 경보가 발송되어 사용자 알림 피로(Alert Fatigue)가 발생합니다. ConcurrentHashMap 기반 5분 쿨다운으로 이를 해결했습니다.

CongestionAlertProducer.java — 혼잡 경보 중복 억제
// 역명:노선코드 복합 키 — 같은 역의 다른 호선은 독립 쿨다운 관리 private final ConcurrentHashMap<String, Long> lastAlertTime = new ConcurrentHashMap<>(); private static final long COOLDOWN_MS = 5 * 60 * 1000L; public void publishIfNeeded(String stationName, String lineNumber, int level) { if (level < THRESHOLD_CROWDED) return; String key = stationName + ":" + lineNumber; // 복합 키 long now = System.currentTimeMillis(); Long last = lastAlertTime.get(key); if (last != null && (now - last) < COOLDOWN_MS) return; // 쿨다운 중 조기 반환 lastAlertTime.put(key, now); // lineNumber 를 파티션 키로 지정 → 같은 호선 이벤트 순서 보장 kafkaTemplate.send(TOPIC, lineNumber, payload); }
설계 포인트상세효과
복합 키 설계역명:노선코드 조합강남역 2호선·신분당선 독립 쿨다운 관리 가능
Lock-free 동시성ConcurrentHashMap 원자적 연산Kafka Consumer 멀티 스레드에서 synchronized 없이 스레드 안전성 확보
파티션 키 설계lineNumber → 같은 파티션동일 호선 이벤트 순서 보장 (Ordering Semantics)

병렬 조회 설계.
⚡
문제 ①: 1호선은 소요산~신창 100개 이상의 역이 존재합니다. 순차적으로 API를 호출하면 수십 초의 지연이 발생합니다.
문제 ②: 서울시 API는 동일 열차를 여러 역에서 중복 반환합니다. 단순 수집 시 같은 열차가 3~4회 등장해 실제 위치를 특정할 수 없습니다.
SubwayLineService.java — 병렬 조회 + ETA 기반 중복 제거
// I/O 전용 50-스레드 풀 — ForkJoinPool.commonPool은 CPU 코어 수에 묶여 부적합 private static final ExecutorService FETCH_POOL = Executors.newFixedThreadPool(50, r -> { Thread t = new Thread(r, "subway-fetch"); t.setDaemon(true); return t; }); // trainNo 기준 중복 제거 — ETA 최솟값(= 가장 가까운 역) 유지 Map<String, ArrivalDetail> trainMap = new ConcurrentHashMap<>(); List<CompletableFuture> futures = stations.stream() .map(station -> CompletableFuture.runAsync(() -> { for (ArrivalDetail d : seoulClient.fetchArrivalDetails(station)) trainMap.merge(d.getTrainNo(), d, (e, n) -> n.getEtaSeconds() < e.getEtaSeconds() ? n : e); }, FETCH_POOL)).collect(Collectors.toList()); CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
기술 선택설계 이유 및 효과
전용 50-스레드 I/O 풀 ForkJoinPool.commonPool은 CPU 코어 수(보통 8~16)에 제한되어 I/O 바운드 작업에 부적합. 전용 풀 50개로 각 역 API 호출을 동시에 처리, 네트워크 대기 중 블로킹 없음
ETA 최솟값 기반 중복 제거 동일 열차가 여러 역에서 중복 반환 → merge()의 remappingFunction에서 ETA가 더 작은(= 더 가까운 역의) 데이터 선택. 열차의 실제 다음 정차역을 정확히 특정
급행·특급 통과역 필터링 btrainSttus + arvlMsg2 교차 검증으로 급행이 정차하지 않는 역을 "다음 역"으로 표시하는 버그 백엔드에서 원천 차단
10초 서버사이드 캐시 ConcurrentHashMap 캐시로 중복 요청 즉시 반환. 외부 API 과부하 방지 및 응답 속도 향상
✅
결과: 1호선 100개 이상의 역을 병렬로 동시 조회하여 응답 시간을 순차 대비 대폭 단축. 열차 중복 제거로 노선도에 동일 열차가 여러 위치에 표시되는 UI 버그를 완전히 해소했습니다.

경로 탐색 —
0-1 BFS 알고리즘.
🧭
왜 Dijkstra가 아닌 0-1 BFS인가?
지하철 경로의 "비용"은 환승 횟수입니다. 같은 노선 이동(비용 0)과 환승(비용 1)이 혼재하는 이 문제에서, Priority Queue가 필요한 Dijkstra(O(E log V))보다 Deque 기반 0-1 BFS(O(V+E))가 더 단순하고 효율적입니다. 상태 공간을 (역명, 탑승 노선) 쌍으로 정의해야 환승역에서 어느 노선을 타고 있는지 구분할 수 있습니다.
