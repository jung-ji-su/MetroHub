프로젝트 정의 및 핵심 역량

MetroHub는 서울시 공공 API에서 수집한 실시간 지하철 데이터를 Kafka 스트림으로 처리하고, SSE를 통해 클라이언트에 Push하는 이벤트 기반 실시간 플랫폼입니다. 단순 CRUD 서버를 넘어, 데이터 수집 → 스트림 처리 → 실시간 전달 → 프론트엔드 렌더링까지 전체 파이프라인을 직접 설계하고 구현했습니다.

⚡
대용량 실시간 처리
50-스레드 전용 I/O 풀로 수백 개 역 병렬 조회, Kafka 파티션 키로 이벤트 순서 보장
🏗️
분산 인프라 설계
SSE 커넥션 격리를 위한 MSA 분리, k8s HPA·Ingress·PVC 포함 전체 인프라 구성
🚀
CI/CD 자동화
4개 서비스 테스트→빌드→배포 완전 자동화, 빌드 번호 태그 기반 롤백 전략 수립

03   Deep Dive & Troubleshooting

엔지니어링 디테일 — 핵심 구현 분석

🔔
Kafka 스트림 처리 — 혼잡 경보 중복 억제 설계
💡
문제 정의: 혼잡도가 80% 이상인 역의 데이터는 30초마다 Kafka에 수신됩니다. 임계값 판단만 있으면 10분 지속 시 20번의 경보가 발송되어 사용자 알림 피로(Alert Fatigue)가 발생합니다.
CongestionAlertProducer.java
@Service public class CongestionAlertProducer { private static final long COOLDOWN_MS = 5 * 60 * 1000L; // 5분 쿨다운 // 역명:노선코드 복합 키 — 같은 역의 다른 호선은 독립 관리 private final ConcurrentHashMap<String, Long> lastAlertTime = new ConcurrentHashMap<>(); public void publishIfNeeded(String stationName, String lineNumber, int congestionLevel) { if (congestionLevel < THRESHOLD_CROWDED) return; String key = stationName + ":" + lineNumber; long now = System.currentTimeMillis(); Long last = lastAlertTime.get(key); // 쿨다운 중이면 조기 반환 — Lock 없이 원자적 읽기 if (last != null && (now - last) < COOLDOWN_MS) return; lastAlertTime.put(key, now); // lineNumber 를 파티션 키로 지정 → 같은 호선 이벤트 순서 보장 kafkaTemplate.send(TOPIC, lineNumber, payload); } }
설계 포인트상세 구현효과
복합 키 설계 역명:노선코드 조합 사용 강남역의 2호선/신분당선 독립 쿨다운 관리
Lock-free 동시성 ConcurrentHashMap 원자적 연산 Kafka Consumer 멀티 스레드 환경에서 synchronized 없이 스레드 안전성 확보
파티션 키 lineNumber → 같은 파티션 라우팅 동일 호선 이벤트 순서 보장 (Ordering Semantics)
경보 등급 ≥90% VERY_CROWDED 🔴 / ≥80% CROWDED 🟠 프론트엔드 경보 카드 색상 차별화
🗺️
실시간 노선도 — 전체 역 병렬 조회 + 중복 제거 알고리즘
🔍
문제 정의: 1호선은 소요산~신창까지 100개 이상의 역이 존재합니다. 순차 API 호출 시 수십 초 지연이 발생하며, 서울시 API는 동일 열차를 여러 역에서 중복 반환하여 열차 위치 특정이 불가합니다.
SubwayLineService.java
// I/O 전용 50-스레드 풀 — ForkJoinPool.commonPool 미사용 (CPU 코어 수 제한 회피) private static final ExecutorService FETCH_POOL = Executors.newFixedThreadPool(50, r -> { Thread t = new Thread(r, "subway-fetch"); t.setDaemon(true); return t; }); // trainNo 기준 중복 제거 — ETA 최솟값 유지 (= 실제 다음 도착역) Map<String, ArrivalDetail> trainMap = new ConcurrentHashMap<>(); List<CompletableFuture<Void>> futures = stations.stream() .map(station -> CompletableFuture.runAsync(() -> { List<ArrivalDetail> details = seoulClient.fetchArrivalDetails(station); for (ArrivalDetail d : details) { if (!lineCode.equals(d.getLineCode())) continue; // 동일 열차는 ETA가 더 작은(가까운 역) 데이터로 교체 trainMap.merge(d.getTrainNo(), d, (existing, newer) -> newer.getEtaSeconds() < existing.getEtaSeconds() ? newer : existing); } }, FETCH_POOL)) .collect(Collectors.toList()); CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
기술 선택이유
전용 50-스레드 I/O 풀 ForkJoinPool.commonPool은 CPU 코어 수에 묶여 I/O 바운드 작업에 부적합. 명시적 풀 선언으로 네트워크 대기 중 다른 역 조회 블로킹 방지
ETA 최솟값 중복 제거 동일 열차가 여러 역에서 중복 반환 → ETA 최소값 역이 실제 "다음 도착역"임을 역산하여 위치 특정
10초 서버사이드 캐시 ConcurrentHashMap 캐시로 중복 요청 차단, 외부 API 과부하 방지
급행·특급 통과역 필터링 btrainSttus + arvlMsg2 교차 검증으로 정차하지 않는 역을 다음 역으로 표시하는 버그 원천 차단

경로 탐색 알고리즘 — 왜 Dijkstra가 아닌 0-1 BFS인가

📐 알고리즘 선택 근거

지하철 경로 탐색의 "비용"은 환승 횟수입니다. 같은 노선 내 이동(비용 0)과 환승(비용 1)이 혼재하는 이 문제는 Priority Queue가 필요한 Dijkstra보다 Deque 기반 0-1 BFS가 더 단순하고 O(V+E)로 더 효율적입니다.

routeCalculator.js
// 상태 공간: (역명, 탑승 노선) 쌍 — 환승역에서 어느 노선 탑승 중인지 구분 export function findRoute(from, to) { const dist = new Map(); // "역명:노선코드" → 최소 환승 횟수 const deque = []; // 출발역의 모든 노선을 비용 0으로 초기화 for (const line of STATION_LINES[from]) { dist.set(`${from}:${line}`, 0); deque.push({ station: from, line, transfers: 0 }); } while (deque.length > 0) { const { station, line, transfers } = deque.shift(); if (station === to) return buildSegments(prev, `${station}:${line}`); // 같은 노선 인접 역 → 비용 0 → deque 앞에 삽입 (unshift) for (const delta of [-1, 1]) { const nk = `${ls[idx + delta]}:${line}`; if (transfers < (dist.get(nk) ?? Infinity)) { dist.set(nk, transfers); deque.unshift({ station: ls[idx+delta], line, transfers }); // ← 비용 0 } } // 환승 → 비용 1 → deque 뒤에 삽입 (push) for (const otherLine of STATION_LINES[station] ?? []) { if (otherLine === line) continue; const ok = `${station}:${otherLine}`; if (transfers + 1 < (dist.get(ok) ?? Infinity)) { dist.set(ok, transfers + 1); deque.push({ station, line: otherLine, transfers: transfers+1 }); // ← 비용 1 } } } return null; }
항목0-1 BFSDijkstra일반 BFS
시간 복잡도 O(V+E) O(E log V) 최단 경로 보장 불가
자료구조 Deque (unshift/push) Priority Queue Queue
비용 조건 0 또는 1 (환승 여부) 임의 양수 균일 비용만 가능
이 문제 적합성 최적 과도한 복잡도 부적합
📐
소요 시간 추정: 경로 탐색 완료 후, 노선별 평균 역간 이동 시간 (GTX-A: 300초 / 경의중앙선: 200초 / 1~9호선: 90~130초)과 환승 시간(평균 3분)을 세그먼트별로 합산하여 총 소요 시간을 추정합니다.

실제 장애 6종 — 원인 분석 및 해결책
#장애 상황원인 분석적용한 해결책
01 Kafka 재시작 후 .lock 파일로 무한 CrashLoopBackOff 비정상 종료 시 PVC에 .lock 잔류 initContainer에서 파드 시작 전 .lock 삭제 + chown 실행
02 Kafka 브로커 초기화 실패 — 자기 자신 Service 탐색 불가 k8s가 KAFKA_* 환경변수 자동 주입 → Confluent 설정값 덮어씌움 enableServiceLinks: false 로 자동 주입 차단
03 Kafka 파드 교체 시 신규 파드가 볼륨 마운트 실패 PVC ReadWriteOnce — 동시 마운트 불허 Deployment strategy.type: Recreate 적용 — 구 파드 완전 종료 후 기동
04 Kafka PVC 쓰기 실패 (Permission Denied) Confluent 이미지 프로세스가 appuser (gid 1000)으로 실행 securityContext.fsGroup: 1000 설정으로 볼륨 그룹 소유권 부여
05 Kafka 브로커가 자신의 Endpoint를 찾지 못해 기동 실패 파드가 준비되기 전 자기 자신에 연결 시도 (chicken-and-egg) Service에 publishNotReadyAddresses: true 설정
06 k8s 배포 환경에서만 JWT 검증 실패 JwtUtil이 env를 base64 디코딩하는데, k8s Secret이 한 번 더 인코딩 secrets.yaml에 JWT 시크릿을 double base64 인코딩하여 원본값 확보
🎯
원클릭 배포 스크립트 (k8s-deploy.ps1): Namespace → Secret/ConfigMap → MySQL(kubectl wait --for=condition=ready) → Zookeeper → Kafka(Ready 대기) → 애플리케이션 4종 → HPA/Ingress 순서를 자동 조율. 의존성 있는 컴포넌트를 동기화하여 타이밍 이슈를 원천 차단했습니다.

08   Database Schema

핵심 DB 설계

테이블설명주요 설계 포인트
users 회원 (username, password_hash, nickname) BCrypt 해시, JWT Stateless 인증
congestion_data 실시간 혼잡도 캐시 역별·호선별 upsert로 항상 최신 상태 유지
congestion_hourly 시간대별 누적 평균 (0~23시) ON DUPLICATE KEY UPDATE로 이동 평균 점진적 집계
community_posts 게시글 (호선 태그, 공지 플래그) line_number 인덱스로 호선별 필터 성능 확보
post_likes 좋아요 user_id + post_id UNIQUE 제약으로 중복 좋아요 DB 레벨 차단
complaints 민원 (상태 머신) RECEIVED → IN_PROGRESS → COMPLETED 상태 전이
notifications 알림 이력 user_id nullable = 전체 공지 / not null = 개인 알림
subscriptions 호선 구독 user_id + line_number UNIQUE로 중복 구독 차단
